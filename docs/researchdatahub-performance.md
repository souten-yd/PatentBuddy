# ResearchDataHub — ストレージ効率・低ディスク I/O・大量データ性能（Codex 実装契約）

**状態:** 2026-11-10 設計決定。現行 `main` に未実装の最適化を、実装済みと混同しない。
**優先度:** 最優先の非機能要件。対象は特許、規格、論文、技術資料、将来の複数DB。実装本体は `ResearchDataHub`、高度な検索/推論は `PatentBuddy` ControlDeck Add-on。

## 1. 目標と禁止事項

1. **正確さ・復元可能性を性能より優先。** 正本DBはその時点で1台のみ。開発中は ControlDeck PC の**ローカル SSD**、移行後は QNAP の**ローカルファイルシステム**。PCとNASの間でSQLite/WALを直接共有しない。転送は認証付きAPIまたは一貫したバックアップのみ。
2. 無変更データの再投入、GET/検索、アイドル状態からの不要な書き込みを可能な限り**ゼロ**に近づける。ただし認証失敗/必要な監査・保持期間・整合性を犠牲にしない。
3. 1万件でも100万件でも**全件をPythonメモリへ読み込んでから絞り込む**方式を採用しない。索引、カーソル、バッチ、必要列のみ取得を優先。
4. **SQLiteの安全設定を弱めない**: `journal_mode=WAL`、`foreign_keys=ON`、`synchronous=NORMAL` は現行の前提。任意の `journal_mode=OFF`、`synchronous=OFF`、`fsync` 無効化、全件を毎回 `VACUUM`、無制限同時書込みは禁止。同期レベルを変える場合は停電/クラッシュ時の喪失可能性を明示して別途承認を得る。
5. 保存容量だけでなく**読み書き総量・レイテンシ・CPU・RSS・索引更新・再起動時間**を比較する。原文の圧縮/重複排除は「より速い」と決めつけない。CPU時間とSSD/HDD転送量を両方測定する。
6. ストレージ不足、再起動、ネットワーク断、部分取り込み、二重送信、コネクタのレート制限時に**取り込みを安全に中断/再開**できる。サイレントなスキップや二重登録は禁止。
7. 公開資料も著作権・契約条件により再配布可能とは限らない。通常の索引と、外部AI向け手動承認済み抜粋は別アクセス権限。未公開発明/請求項はローカルLLMにのみ入力可。

## 2. 既存実装の現状（2026-11-10 `main` を確認）

- `qnaplibrary/store.py`: SQLite 1接続 + `threading.RLock`、WAL、`synchronous=NORMAL`、64 MiB page cache、256 MiB mmap、`wal_autocheckpoint=2000`、`busy_timeout=30000`、FTS5日本語2-gram、`BEGIN IMMEDIATE` を利用。
- `add_documents`: 最大5,000件/要求・1要求1トランザクション、内容ハッシュで同一文献をスキップするが**文献ごとに重複照合 SELECT**、全件無変更でもコレクション更新日時を UPDATE。検索索引作成を同トランザクション内で実行。
- `list_documents`: `SELECT *` で本文をDBから読み、Pythonで長さを計算して破棄。深いページで遅くなり得るOFFSET方式。
- `fts_search`: FTS5が使えればBM25、無い環境はLIKEスキャン。FTS5の可用性/クエリプランは環境ごとに確認が必要。
- `q()` は `fetchall()`、単一SQLite接続でRLockを共用。巨大な集計・読取が取り込みを待たせる可能性がある。**不用意に並列接続を増やさず**、計測・一貫性を検証してから読み取り分離を設計。
- **PR #13（Draft、未マージ）**に重複IDのまとめ読み、無変更時UPDATE省略、必要列のみ一覧、安定IDカーソル、性能テスト/ベンチを準備中。**mainに入っていると誤認しない。**

## 3. 優先する実装（小さく独立したPRで進める）

### Phase P0 — 計測基盤（先行）
- ランタイム構成、SQLite/FTSバージョン、CPU/メモリ、ストレージ種別、DB・WALサイズを明記して基準値を採る。
- 明示実行の `scripts/bench_datahub.py` を設計（現存のPR #13の `scripts/bench_patents.py` を汎用化）。**既存のユーザーデータに書き込まず、tempディレクトリの合成データだけ**を使用。10³/10⁴/10⁵件で登録、同一再送、更新、ID完全一致、キーワード検索、絞り込み、1ページ/深いページの性能を計測。10⁶件はディスク容量・時間・RSS見積り後の明示実行とする。
- 指標: docs/s、MiB/s、API P50/P95/P99、SQL時間、SQLite `total_changes`、DB/WAL/SHMの増分、物理デバイス read/write bytes、process RSS、CPU、FTS/ベクトル索引容量、再起動時間。`total_changes` のゼロだけでは物理I/Oゼロの証明にならない。
- アイドル時（収集・更新・バックアップなし）の15分間と、負荷時の物理読み書きを**別計測**。PC（SSD）と移行予定のQNAP（HDD）で独立結果を取る。監視自体が書込みを発生させないこと。

### Phase P1 — 冪等取り込み/ページング（PR #13をレビューし統合）
- `(collection_id, ext_id)` を唯一の冪等キーとし、バッチ内ID重複でも最終文献の値が正しいこと、原文と派生chunk/FTSが一致することをテスト。キー無し文献は重複保証の範囲外と明記。
- 同一要求の外部IDをSQLiteのパラメータ上限に収まる単位でまとめて照合。差分なしでは文献・コレクションupdated・FTS・ベクトルを変更しない。読み取りのみの無変更バッチでは可能なら `BEGIN IMMEDIATE` 自体を省くが**TOCTOU/競合を防ぐ**。更新時はバッチで一貫したコミット。
- 文献一覧は **メタデータと本文長のみSQLで取得**、本文は明示詳細表示時に遅延取得する。通常は既存OFFSET APIと互換、新規バルククライアントはIDカーソル方式（最初 `cursor=start`）を使用。安定ページ境界・途中追加・削除・最終ページをテスト。
- 番号完全一致・出願人・規格番号などは索引ベースにする。参照元/改版の検証を残し、全件スキャン検索を常用しない。
- データの整形・圧縮・外部API取得はトランザクション前の計算に切り出すことを**計測して検討**。同一文献の複数並行取り込みでも値・更新順序が破綻しないこと。

### Phase P2 — 保存効率とFTS/構造化フィルタ
- 文献本文をSQLiteに無制限に重複保存しない。原文/正規化テキスト/分割chunk/埋め込み/分析キャッシュの役割を明確化し、文献単位のハッシュで重複を検知する。**FTS5の索引は検索品質と更新コストを測って調整**、無条件の全文再構築は禁止。
- 規格番号（JIS/ISO/IEC）、規格版、ICS、特許公開/出願番号、ファミリー、IPC/CPC、日付は正規化したフィールド/索引を設計。検索SQLの `EXPLAIN QUERY PLAN` で意図した索引利用を確認。複合索引の追加は容量・書込み増を必ず比較。
- 原本（PDF/HTML等）の大きいバイナリは、必要時に**内容ハッシュに基づく独立blob保管**を検討（SQLiteに二重格納しない）。圧縮形式・重複排除・blob GC・改版/参照保護は互換移行と復元テストを伴う別PR。PDFの著作権と原本確認を維持。
- 分析集計はバージョン付きキャッシュ/変更通知で必要時再計算。閲覧ごとに集計更新を書き込まない。巨大なCSV/NDJSONは逐次読み書き・ページ単位転送で上限を設定。

### Phase P3 — 同時アクセスとNASへの移設
- リードの並行性を上げる必要があれば、**読み取り専用SQLite接続プール**とwriterの分離をベンチで比較。ロック時間・コミット待ち・checkpoint・snapshot整合性を必ず検証。現行の1接続を無条件に変更しない。
- WALチェックポイントは負荷/増分と連動し、HDDに細かいランダムI/Oを繰り返さない方針。大きなWAL無制限放置もしない。既存 `wal_autocheckpoint` の安易な削除/無効化は不可。
- NAS移行はSQLite online backup/停止時整合コピー→`PRAGMA quick_check`→文献数/ハッシュ/機密設定/認証・パスキー/秘密情報を検証→切替、失敗時ロールバック。**PCとNASで同時に正本を稼働させない**。
- ControlDeckのLLM/GraphRAGとベクトル索引はPC側。NAS側はコンパクトなAPI結果/必要な根拠断片を返す。LLM/埋め込みの処理進捗はユーザー向けに表示するが、1トークンごとにDBへ書かない。

## 4. Codex の受入ゲート（PRごとに必須）

- **正しさ:** 全既存テスト＋追加テスト成功。再送/重複/部分失敗/終了直前の強制停止/再起動/復元後の検索結果一致。管理セッション・パスキー・private/public権限・外部LLM遮断が維持される。
- **性能:** 同一マシン/入力/SQLite設定で変更前後比較。差が小さければ採用しない。追加索引とキャッシュのディスク費用を報告。遅くなったケースと妥当な理由をPR本文に残す。
- **I/O:** 取り込み時・無変更再送時・アイドル時のディスクread/write_bytesとDB/WAL増分を記録。**無変更再送で永続行更新がないこと**、通常検索で不要なDB書込みがないことを確認。
- **安全性:** 認証・CSRF・秘密値の扱いを維持、任意実行やroot処理を増やさない。FTS5の無い環境の代替経路をテスト。フルDB読み込み・無制限バックグラウンド索引構築・起動時の毎回再構築は禁止。
- **配布:** `bash scripts/verify.sh` と `bash scripts/build-linux.sh dist` をLinux PCで実行し、結果をHANDOFF/PRに記録。QPKGを変える場合はQPKGビルドも確認。実機がなければ**未検証と明記**。
- **ドキュメント:** `docs/HANDOFF.md`、本書、`docs/researchdatahub-plan.md` を同期。各PRで実施/未実施・ベースSHA・予定する次のPRを残す。計測のための常駐デーモンや新CIを無断追加しない。

## 5. スコープと既存PRの優先順

- 本計画は **性能要件の定義**。PR #16 はドキュメントの引き継ぎチェックポイントであり、速度改善・新DB・GraphRAGの稼働を実装完了とは扱わない。
- 最初の性能実装は **PR #13 の差分を現行mainに突き合わせ、テストを修正して小さく統合**。DBスキーマ/パッケージの互換と既存の機密保護PR #12を損なわないこと。
- PR #15 はpublished-only APIの機密保護を独立レビュー、PR #14 はHost A0安全境界を独立レビュー。性能改善と混ぜない。
- **性能目標の数値はベースライン取得後に設定**。100万件対応や低I/Oを測定前に保証しない。
