# 調査キュー・絞り込み・収集の分担

2026-11-11 ユーザー指定を反映した実装契約。未実装の設計を含み、完了状況はHANDOFFに記録する。

## 基本配置

ResearchDataHubを唯一の正本・調査キューの所有者とする。開発中はLinux、最終配置の第一候補はQNAP。PatentBuddy/ControlDeckはPC計算workerと対話UI。GPUが必要な検索工程があることだけを理由にNAS保存を廃止しない。

|責務|QNAP ResearchDataHub|Linux PatentBuddy / ControlDeck|
|---|---|---|
|正本|PDF/画像/抽出本文/書誌/版/関係/監査/結果/キュー|保持しない。索引と処理中ファイルは再構築/削除可能|
|外部収集|許可された公開検索式の公式API/RSS取得、低並列PDF保存|必要時に同じ収集jobをleaseして代行、結果をAPI返送|
|検索|全文/構造化メタデータ、ページング、集計|埋め込み、vector/ANN索引、rerank、意味分類|
|分析|処理待ち/結果受領/整合性確認|OCR、ローカルLLM、請求項/関係提案、絞り込み提案|
|資源|CPU/RAM/ネットワーク/I/Oの低い固定上限|ControlDeck Host Jobs/CPU・GPUリース|

GPUなしでも書誌検索・収集・重複排除・格納は実行可能。rerankは候補集合にだけ適用し、全公報へ毎回実行しない。PC停止中はGPU必要jobを待機し、OpenRouterへ切り替えない。NASの低速CPUと外部送信の機密リスクを混同しない。

## 調査の段階

1. キーワード、目的、最大取得公報数（初期10件）、最大取得bytesを設定。外部に送る検索式は実行前に全文表示し承認。承認はその式/版に結び付ける。
2. 公式APIで書誌/要約/分類/ファミリー/取得可能形式を先に収集。PDF全文はまだ取得しない。検索応答の総件数、実取得候補件数、取得上限/未取得ページを分離表示。総件数不明・ページ上限で打切りの場合に網羅検索済みと表示しない。
3. 公報番号+国+kind+言語で同一公報を統合し、出典URLを複数保持。ファミリーは一発明のグループとして集約するが、各国の請求項差や公開/登録/補正公報を削除しない。ファミリー不明は推測で統合しない。ダウンロード済SHA/版を照合して再取得不要の同一内容を省く。
4. 技術対象×検知手法（パワエレ例: インバータ/半導体/コンデンサ/巻線 × 電流波形/電圧/温度/モデル残差/機械学習）をヒートマップ表示。年代/出願人/IPC・CPC/国/言語を追加filterにできる。意味分類はローカルLLMで提案し、根拠/信頼度/未分類を残す。色は該当件数であって新規性や特許性の評価ではない。
5. セルを一時マスクして除外/再表示。原データは削除しない。多重分類の公報はID集合で数え、セルの件数単純合計を採用数にしない。低信頼/未分類を黙って除外しない。候補IDと検索snapshot版にマスクを結び付け、更新時に選定を見直す。
6. 上限超過中はダウンロードを開始せず、分類/期間/代表公報等の絞り込みを理由付きで提案。暗黙の先頭N件取得は禁止。既定は1ファミリー1代表公報、日本語優先/取得可能な公式PDFを優先し、国別の権利比較時は複数公報を明示選択。上限は実際の公報ファイル数とbytesで判定する。
7. 最終対象/除外理由/国・言語・kind/既存原本/取得元/最大bytesを表示。ユーザーが「この条件で上限内なら取得」を実行すると承認済みsnapshotだけキューへ投入する。候補集合変更・予算超過・上限不明は停止。低並列取得、取消、失敗だけ再開、hash検証後に正本へ確定。
8. PC workerが必要な原本だけ取り出してOCR/抽出/LLM/rerankを実行し結果と原文範囲・モデル版を返送。採用/却下は人手操作。比較表・根拠図・未確認点を提示する。

## キュー契約

- 正本DBのjobは依頼者/検索snapshot/入力版/段階/能力要件/件数bytes上限/idempotency keyを保持。PCのHost Job IDと対応付け、二つの独立した原本文献DBを作らない。
- job状態はdraft → discovering → awaiting_selection → ready → leased → running → succeeded/failed/canceled。段階別の再試行を持ち、PC不在はfailed扱いにせずwaiting_for_workerを表示する。
- workerは認証済APIでpull/claim。短期leaseと世代番号による完了の競合防止、期限切れ再配布、入力版の再確認、冪等な結果確定が必要。NASのleaseは調査仕事の所有権、GPU leaseはControlDeckが管理する計算資源であり区別する。
- 外部API鍵/パスワードをjob本文やGETへ含めない。scope付きworker権限。秘密の検索語・発明本文から外部検索式を無断で作らない。公開公報でも私的メモ・選定理由・未公開請求項を混ぜてクラウドへ送らない。外部AIは既定不使用。
- 正本SQLite/WALはNASローカルfilesystem。PCはHTTPS APIだけを利用し、SMB/NFSからDBを直接開かない。アイドル時の頻繁なDB更新を避け、進捗は間引き、batch確定、lease更新頻度に上限を持つ。

## 配置の受入

QNAP実機で書誌1千/1万/10万、原本取り込み、検索/ヒートマップP50/P95/P99、CPU/RSS、DB/WAL増分、物理read/write、15分idle、PC切断/再開、復元を計測する。Linuxの計測結果をQNAPの保証にしない。数値目標は測定後に定める。

遅い場合は、まず並列数/一括取得量/索引/転送断片とPC側キャッシュを調整する。それでも正本DBの操作が利用条件を満たさなければ、最後に単一正本DBをPC SSDへ移す選択肢を検討する。大容量原本のNAS保持はその場合も別途維持可能だが、API越し原本ストレージとバックアップ/復元の整合性を設計してから変更する。現時点ではNAS移行を放棄せず、同時二重書込みもしない。
