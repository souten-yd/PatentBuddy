# 軽量保存と検索の推奨構成

2026-11-19。開発方針と受入条件。全体は実装途中。

## 推奨

全文・請求項・書誌・図の説明・出典対応を保持し、重要図を可逆圧縮で保存する。公開PDFは取得元・公開番号・公報種別・取得日・原本hashを記録して必要時に再取得する。再取得不能や版違いを表示する。利用者が保存指定した重要原本を保持できる設定を用意する。未公開資料はローカル保存とする。

SQLite正本とFTS5全文検索を維持する。図の説明も検索対象にする。通常検索はLLMの稼働状況に依存させない。意味検索はPC上のQdrantによる再生成可能な索引を評価し、キーワード結果と統合する。ローカルAIの回答生成は検索結果と根拠を入力して明示操作で行う。NAS移行後もSQLite/WALはNASのローカルディスクに配置する。

2万件の保存データ約2GBは、日米半々・画像容量25%保持を仮定した試算。検索索引・ベクトル・一時領域・バックアップの容量を別計上する。全体5〜10GBという以前の会話上の枠は未検証。実データで測定して確定する。画像を学習したモデルによる圧縮は研究候補であり、可逆画像の標準保存を先行する。

## 今回の検索修正

日付条件を全文検索のLIMIT前に適用する。FTS5とLIKE、緩いOR検索のいずれも同条件を使う。期間指定の意味検索はSQLiteの現在の日付に合うchunk IDを使用して、ローカルのベクトル候補を上位選択前に制限する。Qdrantの既存payloadは日付を持たないため、この期間検索はローカル経路を明示する。日付指定なしのQdrant経路は従来どおり。

この期間指定経路は正確さのための暫定実装であり、候補ID集合と既存ベクトル索引のRAM使用・全走査コストがある。高速化完了としない。次工程でQdrantの日付payload/index、既存ポイントの移行、文献の日付更新・削除・障害復旧の同期を実装・測定する。索引が古い場合の欠落を防ぐこと。

## 次の受入

1. 保存ポリシーを文献単位で持つ。再取得できる公開原本の省略、重要図選択、圧縮、原本を再取得するAPIを認証済み手動操作で実装する。既存データの自動削除は行わず、使用量と削除対象を確認できる移行を用意する。
2. 原本・本文・図・AI説明・検索索引ごとの容量を表示し、取得から解析保存までの時間を実測する。AI停止中は図の説明を保留して手動再開する。
3. 実公報の語彙・頁数分布で2万件相当を測る。通常検索P95 1秒、意味候補検索P95 3秒を受入目標とし、初回・反復・同時検索を分ける。これらは保証値ではない。
4. 国・分類・日付の絞り込みを候補取得前に適用し、期待文献の漏れと引用箇所の対応を検証する。全文検索・意味検索・AI回答の所要時間を別表示する。
