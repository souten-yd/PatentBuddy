# 大規模特許データ対応 — 段階的な実装計画

対象: QnapPatentBuddy / QNAP TS-253Be（メモリ16GB想定）。既存 SQLite + FTS5 を基礎とし、別PC・Qdrant を必要に応じて利用。

## 設計原則
- 特許公報の原文、公開日、出願人、IPC/CPC/FI/Fターム、根拠箇所を保持し、検索結果の出典を検証可能にする。
- 既存文献の `collection_id + ext_id` は冪等キー。既存データを壊す移行、無条件の再索引、自動削除は行わない。
- NASの書き込みを最小化。バックアップ・管理認証・検索の機能を退化させない。
- 実機測定を前提にする。100万文献での速度を測っていない段階で性能保証しない。

## P1（本PR）: API一括登録と一覧表示の軽量化
- 事前に同一バッチの外部IDをまとめて照会し、1件ずつの重複確認SELECTを削減する。
- 全件重複の再投入時はコレクション更新日時を**書き換えない**。
- 一覧取得は本文全文をPythonメモリへ転送せず、メタデータのみSELECT。結果の形式は維持する。
- 公開番号などの厳密な文献ID検索は `?ext_id=...` で複合UNIQUE索引を利用する。
- 大きいオフセットの代替として `GET /api/v1/collections/{cid}/documents?cursor=ID&limit=...` による降順IDカーソルを追加する。従来の offset パラメータは互換維持。
- `(collection_id,id DESC)` 索引は初回起動時に一度だけ作成。既存SQLiteの再作成なし。
- テスト: 重複を含むバッチの最終値、更新0の無書込、ページ境界/追加挿入、旧API互換、クエリプラン確認。

## P2（次PR）: 特許検索の拡張
- 公報番号/出願番号の正規化と正規形キー、priority date / application date / IPC 等の構造化フィルタ。
- 保存形式のフィールド整合、索引ベースの出願人・分類・年度絞り込み。
- クエリ実行プランの収集（管理者・明示実行のみ）、P50/P95目標設定。
- 分析画面の重い集計をキャッシュまたは事前集計（更新があった場合にだけ再計算）。
- 大量NDJSONはクライアント側バッチ分割、途中失敗/再開、件数・エラー履歴、レート上限を設計。

## P3（次々PR）: 検索バックエンドとAI分担
- FTS5が無いQNAP Python環境では性能低下を明示し、FTS5対応Python/SQLiteの導入経路を検討。
- 大規模ベクトルはQdrantのディスク索引を利用、RAMにすべて載せない。容量・I/O・復元の整合性を確認。
- OCR・PDF解析、埋め込み生成、重いLLMをPC/GPU側で行い、NASへ検証済み構造データをAPIで送信。

## ベンチマーク・受入基準
- 合成 1千/1万/10万文献および実際の公報サンプルで、登録件数/秒、冪等再投入、ページ取得、キーワード検索 P50/P95、WAL/SSD/HDD書込量、最大RSSを採取。
- NAS稼働中の応答性・RAM消費・CPU・ディスクアクセスを確認して段階的に最適化。
- 検証環境の結果と実機結果を区別する。基準値は測定結果に基づいて決定する。
